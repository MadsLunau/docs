title: "Parahelp Support API"
---

The Parahelp Support API connects your product to a Parahelp Customer Agent. You send events (a customer message, an order update, a failed job etc) into a session, the Customer Agent reacts to them with its knowledge and tools, and your backend reads the results back.

Use it to:

- **Power your own in-app agent or chat.** Parahelp runs in the background; your users only ever see your UI.
- **Connect a channel Parahelp doesn't support natively.** A small relay forwards the channel's webhooks as events, and a custom tool replies through the channel's API.
- **Feed product context into a conversation.** Send events like a failed payment or a status change into an open session, and the agent takes them into account.
- **Bring your own agents.** An agent you run on your own infrastructure can pick up escalations and post answers back, without Parahelp ever reaching into your network.

The complete specification is in the [API Reference](/api-reference). This page covers the concepts and the typical flow.

## How it works

Every integration does two things: it sends events into Parahelp, and it delivers the Customer Agent's output back to your user.

| Part | Responsibility |
| --- | --- |
| **Your backend** | Holds the API key, sends events, reads results and decides what to show users. |
| **Parahelp Customer Agent** | Reads the session's events, uses its knowledge, memory and tools, and acts: replies, takes an action, or escalates. |
| **Your product or channel** | Where users write and where they see replies. |

Sending an event and getting a reply are separate operations. Every write returns `202` as soon as the event is recorded; the Customer Agent runs asynchronously.

### Sessions

A session is a list of events. "Session" in the API and "ticket" in Parahelp mean the same thing: an in-app chat, a Slack thread or an email thread can each be one session.

Generate a unique id per conversation, typically a UUID, and send it as `session_id` with every event. The first event creates the session. Parahelp stores it with an `api_session_` prefix and returns that full id in every response; either form works on later requests. Ids are matched case-insensitively and can be up to 128 characters (letters, digits, `.`, `_`, `:` and `-`).

### Events

An event is something that happened. A customer message is one kind of event, but so is "order shipped", "job failed" or "subscription renewed". Data event payloads are free-form JSON, and the Customer Agent sees exactly what you sent.

Two payload types are understood without further instructions:

| `payload.type` | Use it for |
| --- | --- |
| `customer_message` | What a customer wrote. |
| `parahelp_agent_message` | A reply sent by one of your custom tools. |

Neither is required. Anything else, for example `{ "event": "return_requested", "order_id": "5678" }`, works too.

There are two event endpoints:

- **Data event** (`POST /api/v0/support/events/api/data`): anything that happened.
- **Session updated event** (`POST /api/v0/support/events/api/session-updated`): changes which agent profile handles the session and its environment variables.

### Agent profiles

An agent profile defines a Customer Agent: its name, tools, memory and instructions. Profiles are created through the Parahelp agent; ask it for one that runs on API sessions. You can run several side by side, for example one per channel or product area.

List them with `GET /api/v0/support/agent-profiles` and select one for a session by its `agent_profile_id`.

## Authentication

Create and delete API keys in Parahelp under **Settings > API keys** (organization admins only). Send the key with every request:

```bash
Authorization: Bearer <API key>
```

<Warning>
  A key gives full access to your organization's Parahelp API. Keep it on your backend. Never ship it in browser or mobile app code.
</Warning>

All requests go to:

```text
https://external-api.parahelp.com
```

## Quickstart

<Steps>
  <Step title="Find your agent profile">
    ```bash
    curl https://external-api.parahelp.com/api/v0/support/agent-profiles \
      -H "Authorization: Bearer $PARAHELP_API_KEY"
    ```

    ```json
    {
      "agent_profiles": [
        {
          "agent_profile_id": "in-app-support",
          "type": "api",
          "agent_name": "Support Agent",
          "description": "Handles questions from our in-app agent."
        }
      ]
    }
    ```
  </Step>
  <Step title="Send the customer's message">
    ```bash
    curl -X POST https://external-api.parahelp.com/api/v0/support/events/api/data \
      -H "Authorization: Bearer $PARAHELP_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "session_id": "8e2d7a36-3a1c-4a6e-9f21-9d1b8c5e4f10",
        "event_id": "msg-001",
        "payload": {
          "type": "customer_message",
          "message": "My sequence stopped sending yesterday.",
          "user_identifier": "usr_18273",
          "user_email": "jane@example.com"
        }
      }'
    ```

    ```json
    {
      "stored": true,
      "event_id": "api_event_msg-001",
      "duplicate": false,
      "session_id": "api_session_8e2d7a36-3a1c-4a6e-9f21-9d1b8c5e4f10"
    }
    ```
  </Step>
  <Step title="Select the agent profile">
    A new session has no agent profile, so nothing runs yet. A session updated event selects one and sets the values your custom tools need:

    ```bash
    curl -X POST https://external-api.parahelp.com/api/v0/support/events/api/session-updated \
      -H "Authorization: Bearer $PARAHELP_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "session_id": "8e2d7a36-3a1c-4a6e-9f21-9d1b8c5e4f10",
        "agent_profile_id": "in-app-support",
        "environment_variables": {
          "USER_EMAIL": "jane@example.com"
        }
      }'
    ```

    The Customer Agent now runs and sees every event in the session, including the ones sent before the profile was selected. From here on, every new data event asks it to run again.
  </Step>
  <Step title="Read the results">
    ```bash
    curl "https://external-api.parahelp.com/api/v0/support/events?session_id=8e2d7a36-3a1c-4a6e-9f21-9d1b8c5e4f10&type=api_data&type=support_agent_run_finished" \
      -H "Authorization: Bearer $PARAHELP_API_KEY"
    ```

    Replies sent by your reply tool appear as `api_data` events with `payload.type: "parahelp_agent_message"`. A `support_agent_run_finished` event marks the end of a run.
  </Step>
</Steps>

## Replies and actions

By default the Customer Agent can read its memory, write todos and contact the Parahelp agent. **Everything that reaches the outside world, including replying, goes through custom tools** that you add to its agent profile through the Parahelp agent.

A reply tool usually does one of two things:

1. **Writes the reply back to the session** as a `parahelp_agent_message` data event. Your backend picks it up from `GET /api/v0/support/events`.
2. **Delivers the reply directly** through your own API or a channel's API (Slack, email, your chat backend), and returns the result as its tool output.

Actions work the same way: a custom tool can call your own API to look up an account, retry a job or update a record.

Custom tools receive the session's environment variables, plus the session id as `PARAHELP_SESSION_ID`. A tool that uses a Parahelp connection gets a short-lived execution token that works like an API key on this API, so it can post events back without you storing a key in the tool. The token stays valid until 30 seconds after the tool's timeout.

<Info>
  The Customer Agent also sees its own reply events. It recognises them and doesn't act on them again.
</Info>

## Reading data

| Endpoint | Returns |
| --- | --- |
| `GET /api/v0/support/agent-profiles` | Your API agent profiles (up to 1,000, no pagination). |
| `GET /api/v0/support/sessions?type=api` | Your API sessions with their current agent profile and environment variables, newest first. Filter with `environment_variable=NAME:VALUE`, for example all sessions for `USER_EMAIL:jane@example.com`. |
| `GET /api/v0/support/events?session_id=...` | A session's events in recorded order. Only `api_data` by default; repeat `type` to add others. |

Event types you can request:

| `type` | What it is |
| --- | --- |
| `api_data` | Data events you (or your tools) sent. |
| `api_session_updated` | Session updated events you sent. |
| `support_agent_run_started` / `support_agent_run_finished` | Start and end of a Customer Agent run. `finished` includes an `outcome`. |
| `tool_called` / `tool_finished` | Tool calls and their results, linked by `tool_call_id`. |
| `internal_agent_message_received` | Messages from the Parahelp agent to the Customer Agent. |
| `member_message_received` | A message a team member wrote in the ticket for the agent to send as written. |
| `error` | Errors, with an `error_message`. |
| `session_sync_requested` | Requests to process the session again. |

<Warning>
  Show end users only the events you choose. Tool events and Parahelp agent messages can contain memory, search results and internal instructions. Fetch events from your backend, check the viewer's access there, and filter before anything reaches your frontend.
</Warning>

Results are paginated with `next_cursor`. Pass it back unchanged as `cursor`, with the same `session_id` and `type`. `next_cursor` is `null` on the last page; to check for new events, list again from the first page.

## Bring your own agent

If you already run your own agents, Parahelp can loop them in when the Customer Agent needs something only they can answer, such as a lookup against production data or logs.

Your agent doesn't need to be reachable from the internet. It can run on a VM behind your VPN and only make outbound calls:

<Steps>
  <Step title="The Customer Agent escalates">
    When it needs your agent, it records the request in the session through a custom tool (for example a data event with `"type": "internal_escalation"`).
  </Step>
  <Step title="Your agent picks it up">
    Your agent runs on a schedule and polls Parahelp for open requests, using `GET /api/v0/support/sessions` and `GET /api/v0/support/events`.
  </Step>
  <Step title="Your agent posts its answer">
    It sends the answer back as a data event on the same session. That event triggers the Customer Agent, which continues the conversation.
  </Step>
</Steps>

Your production data, logs and internal tools stay behind your network. Parahelp only sees the answers your agent chooses to send.

## Good to know

<AccordionGroup>
  <Accordion title="Asynchronous processing">
    A `202` means the event is recorded, not that the agent has replied. Events that arrive close together, or during a run, may be handled by one run, and the agent can decide to do nothing. A run interrupted by an outage can end without a `support_agent_run_finished` event, so don't wait for it indefinitely.
  </Accordion>

  <Accordion title="Safe retries with event_id">
    Send your own `event_id` together with your own `session_id` on the first request. A retry with the same id, contents and session returns `duplicate: true` and records nothing new. Reusing an `event_id` with different contents or a different session returns `409`. Without `event_id`, every request records a new event.
  </Accordion>

  <Accordion title="Environment variables">
    Use them for values your tools need but the agent shouldn't choose, such as the customer's email for a refund tool. Each session updated event that includes `environment_variables` replaces all previous ones; `{}` removes them all, and omitting the field keeps them. Names use letters, digits and underscores and can't start with a digit.

    **Never put secrets in environment variables.** They are visible to the Customer Agent and stay in the session's event history, even after you change them. Give tools secrets as Parahelp secrets instead. Names that match an existing secret, and `PARAHELP_SESSION_ID`, are rejected.
  </Accordion>

  <Accordion title="Pausing the agent">
    Send a session updated event with `agent_profile_id: null`. The session keeps recording events but no longer runs the Customer Agent until you select a profile again. The same happens if the selected profile is deleted. A run already in progress finishes with the profile and variables it started with.
  </Accordion>

  <Accordion title="Escalations">
    When the Customer Agent can't resolve a session, it contacts the Parahelp agent, which brings in the right people or agents on your team and learns from the resolution.
  </Accordion>

  <Accordion title="Limits and validation">
    Each event can be at most 51,200 bytes as compact UTF-8 JSON. Strings must be valid Unicode; tab, newline and carriage return are allowed, other control characters are not. Numbers must be finite. Rejected events return `422` and are not recorded.
  </Accordion>
</AccordionGroup>

## Errors

Errors return a JSON `detail` field: a message, or a list of problems for most validation errors.

| Status | Meaning |
| --- | --- |
| `400` | The body couldn't be decoded, for example invalid UTF-8. |
| `401` | Missing, invalid, deleted or expired API key or execution token. |
| `403` | Your organization doesn't have Support API access yet. |
| `404` | The `agent_profile_id` doesn't match a configured API agent profile. |
| `409` | The `event_id` was already used with different contents or a different session. |
| `415` | `Content-Type` must be `application/json`. |
| `422` | Validation error: unknown or missing fields, invalid ids, disallowed characters, or an event over the size limit. |
| `500` | Internal error. The event may have been recorded; retry with the same `event_id` and `session_id`. |
| `503` | Session search by environment variable is temporarily unavailable. |
